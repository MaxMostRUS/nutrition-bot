Дата анализа: 2026-07-07

Источник кода для анализа:
- локальная папка `/Users/maxmostovskoy/Documents/БОТ  ПИТАНИЕ` содержит пустой Git-репозиторий без коммитов;
- фактический код был проанализирован из `https://github.com/MaxMostRUS/nutrition-bot`.

## 1. Почему меню сейчас ограниченное

### 1.1. Нет собственной базы рецептов

Сейчас бот не подбирает блюда из каталога рецептов, а просит LLM каждый раз придумать меню с нуля.

Подтверждение в коде:
- `src/controllers/menuController.js:329-405` — недельное меню полностью генерируется через `askChatGPT(...)`;
- `sql/init.sql:18-40` — в БД есть только `menus` и `meals`, но нет таблиц `recipes`, `ingredients`, `tags`, `cuisines`, `dietary_restrictions`, `user_preferences`.

Следствие:
- качество и разнообразие зависят почти только от промпта;
- бот не умеет осознанно расширять меню новыми блюдами;
- нет накопления знаний: удачные рецепты не становятся частью постоянной базы.

### 1.2. Код сам намеренно сужает разнообразие

Промпт явно ограничивает число используемых источников:
- белковые источники: не более 5;
- углеводные источники: не более 3;
- клетчатка/овощи/фрукты: не более 5.

Подтверждение:
- `src/controllers/menuController.js:120-128` — жесткие лимиты по источникам;
- `src/controllers/menuController.js:124-128` — указание "предпочитай уже использованные, не вводи новые";
- `src/controllers/menuController.js:349-360` — эти лимиты реально передаются в генерацию каждого дня.

Следствие:
- на 21 прием пищи в неделю бот сознательно переиспользует узкий набор базовых продуктов;
- особенно ограничение в 3 углеводных базы почти гарантирует повторяемость.

### 1.3. Слишком строгая оптимизация под КБЖУ

Промпт требует очень узкие коридоры:
- калории дня: 99-101% от цели;
- БЖУ дня: 97-103% от цели;
- еще и узкое распределение по каждому приему пищи.

Подтверждение:
- `src/controllers/menuController.js:94-115`.

Следствие:
- модель вынуждена выбирать безопасные, предсказуемые блюда;
- чем жестче математика, тем меньше свободы для интересных рецептов.

### 1.4. Профиль пользователя почти пустой

При регистрации собираются только:
- возраст;
- пол;
- вес;
- рост;
- активность;
- цель.

Подтверждение:
- `src/scenes/registerScene.js:13-173`;
- `sql/init.sql:1-16`.

Не собираются:
- любимые кухни;
- нелюбимые продукты;
- аллергии и ограничения;
- бюджет;
- время на готовку;
- сложность рецептов;
- наличие техники;
- формат питания: 3/4/5 приемов пищи, перекусы, meal prep;
- сезонность;
- семейный формат или одиночное питание.

Следствие:
- бот персонализирует только калории, а не вкус и образ жизни;
- меню математически "персональное", но кулинарно почти универсальное.

### 1.5. Рецепт генерируется после выбора блюда, а не выбирается из надежного источника

Сначала генерируется название блюда и КБЖУ, а потом отдельным запросом придумывается рецепт.

Подтверждение:
- `src/controllers/menuController.js:279-326` — рецепт строится отдельно по имени блюда;
- `src/controllers/menuController.js:377-401` — рецепты генерируются уже после сохранения меню.

Следствие:
- блюдо и рецепт не связаны общей базой;
- КБЖУ и реальный список ингредиентов могут расходиться;
- один и тот же тип блюда может получаться каждый раз очень похожим и неглубоким.

### 1.6. Бот мешает пользователю экспериментировать

Подтверждение:
- `src/bot/utils/menuFlow.js:5-27` — новое меню нельзя сгенерировать чаще, чем раз в 7 дней;
- `src/controllers/menuController.js:330-333` — при одинаковых параметрах меню дополнительно кешируется на 1 час.

Следствие:
- даже если пользователь хочет "дай другой вариант", система сама снижает частоту обновления;
- это усиливает ощущение, что бот умеет мало.

### 1.7. Инфраструктурные ограничения

Подтверждение:
- `src/services/openaiService.js:74-84` — используется один чат-запрос к модели без retrieval-слоя;
- `src/config.js:14` — по умолчанию модель `gpt-4o-mini`;
- `package.json:7` — тестов нет.

Следствие:
- нет RAG, ранжирования рецептов, оценки разнообразия, A/B проверки промптов;
- качество меню трудно стабильно улучшать.

## 2. План действий по улучшению работы бота

### Этап 1. Быстрые улучшения без полной перестройки

Цель: быстро поднять ощущение разнообразия за 3-7 дней.

Сделать:
1. Ослабить ограничения разнообразия в промпте.
2. Убрать правило "предпочитай уже использованные источники".
3. Увеличить пул углеводных и белковых баз.
4. Разрешить 1-2 "интересных" блюда в неделю с более свободным коридором КБЖУ.
5. Добавить режимы меню:
   - `классическое`;
   - `разнообразное`;
   - `быстрое`;
   - `бюджетное`;
   - `высокобелковое`.
6. Добавить кнопку "Сгенерировать альтернативный вариант дня".
7. Разрешить повторную генерацию не раз в 7 дней, а:
   - нового дня сразу;
   - альтернативной недели 1-3 раза в день;
   - полного меню без блокировки для premium.

Ожидаемый эффект:
- меню станет живее даже до появления базы знаний.

### Этап 2. Создать базу знаний рецептов

Это главный шаг.

#### 2.1. Что именно создать

Нужна не просто таблица с текстами рецептов, а нормальная рецептурная база:

- `recipes`
  - `id`
  - `title`
  - `description`
  - `instructions`
  - `servings`
  - `cooking_time_minutes`
  - `difficulty`
  - `cuisine`
  - `meal_type`
  - `source_type`
  - `source_title`
  - `source_url`
  - `license`
  - `embedding`
  - `status`

- `recipe_ingredients`
  - `recipe_id`
  - `ingredient_id`
  - `amount`
  - `unit`
  - `optional`

- `ingredients`
  - `id`
  - `name`
  - `canonical_name`
  - `category`
  - `allergens`

- `recipe_nutrition`
  - `recipe_id`
  - `calories`
  - `protein`
  - `fat`
  - `carbs`
  - `fiber`
  - `portion_weight`

- `recipe_tags`
  - `recipe_id`
  - `tag`

- `user_preferences`
  - `user_id`
  - `favorite_cuisines`
  - `disliked_ingredients`
  - `allergies`
  - `diet_type`
  - `budget_level`
  - `cooking_time_limit`
  - `equipment`
  - `meals_per_day`

- `user_recipe_feedback`
  - `user_id`
  - `recipe_id`
  - `liked`
  - `rating`
  - `cooked_at`

#### 2.2. Чем наполнять базу

Источники в порядке приоритета:
1. Открытые и лицензированные recipe datasets.
2. Собственные вручную проверенные рецепты.
3. Контент с сайта/блога, если есть права на использование.
4. Кулинарные книги только при наличии права на такую загрузку и внутреннее использование.

Практически лучше не "заливать книги как есть", а извлекать из них структурированные карточки:
- название;
- состав;
- шаги;
- кухню;
- тип приема пищи;
- КБЖУ;
- теги;
- допустимые замены.

Идея с книгами хорошая, но лучше делать так:
- не хранить бессистемный большой текст;
- хранить нормализованные рецепты и метаданные;
- при необходимости хранить короткие выдержки и ссылку на источник.

#### 2.3. Как бот должен использовать базу знаний

Новый pipeline:
1. Бот рассчитывает целевые КБЖУ.
2. Фильтрует рецепты по ограничениям пользователя.
3. Подбирает кандидатов по meal type, времени, бюджету, кухне и макросам.
4. Собирает неделю через ranking + constraints.
5. LLM не придумывает блюда с нуля, а:
   - выбирает из кандидатов;
   - делает замены;
   - пишет объяснение;
   - адаптирует порции.

Это намного надежнее, чем текущее "придумай 21 блюдо из головы".

### Этап 3. Перестроить генерацию меню

Текущий подход:
- `LLM -> JSON меню -> отдельный LLM -> рецепт`.

Целевой подход:
- `Recipe KB -> retrieval -> scoring -> weekly planner -> optional LLM formatter`.

Что внедрить:
1. Сервис `recipeCatalogService`.
2. Сервис `nutritionScoringService`.
3. Сервис `menuPlannerService`.
4. Сервис `feedbackLearningService`.
5. Embeddings-поиск по рецептам.
6. Проверку разнообразия на уровне недели:
   - не повторять одну и ту же базу подряд;
   - ограничивать не только названия, но и семейства блюд;
   - учитывать кухни, способы приготовления, главные ингредиенты.

### Этап 4. Расширить анкету пользователя

Добавить в onboarding:
1. Какие кухни нравятся.
2. Какие продукты не нравятся.
3. Есть ли аллергии.
4. Сколько времени готовить приемлемо.
5. Нужны ли быстрые блюда на будни.
6. Нужны ли блюда, которые удобно готовить заранее.
7. Какой бюджет.
8. Нужны ли перекусы.
9. Сколько приемов пищи в день.
10. Есть ли ограничения по технике: духовка, блендер, мультиварка и т.д.

### Этап 5. Добавить обучение на обратной связи

После каждого блюда спрашивать:
- понравилось / не понравилось;
- приготовить еще раз / не показывать больше;
- слишком сложно / слишком долго / слишком дорого.

Это даст:
- персонализацию без ручной перенастройки;
- рост качества меню со временем.

### Этап 6. Технические улучшения

1. Ввести миграции вместо одного `init.sql`.
2. Добавить тесты:
   - парсинг меню;
   - генерация плана недели;
   - фильтры по предпочтениям;
   - агрегация списка покупок.
3. Логировать:
   - какие рецепты выбраны;
   - почему отклонены кандидаты;
   - какие блюда пользователь лайкает.
4. Добавить feature flags для новых режимов меню.
5. Разделить слой LLM и слой детерминированного планирования.

## 3. План действий и структура агентов для разработки бота

Ниже структура именно для команды разработки, а не для runtime-поведения пользователя.

### Вариант организационной схемы

#### Агент 1. Product/Research Agent

Задача:
- формализует продуктовые требования;
- определяет сценарии пользователя;
- описывает режимы меню;
- готовит backlog и метрики качества.

Артефакты:
- PRD;
- user journeys;
- KPI: retention, likes/dislikes, repeat rate, menu diversity score.

#### Агент 2. Recipe Knowledge Base Agent

Задача:
- проектирует схему базы рецептов;
- загружает датасеты;
- парсит источники;
- нормализует ингредиенты, теги и КБЖУ;
- следит за лицензиями и качеством данных.

Артефакты:
- schema;
- ingestion pipeline;
- rules нормализации;
- каталог рецептов.

#### Агент 3. Nutrition Planning Agent

Задача:
- отвечает за расчет КБЖУ;
- проектирует правила подбора рецептов;
- строит weekly planner;
- реализует scoring разнообразия.

Артефакты:
- scoring logic;
- constraint rules;
- planner service;
- quality evaluator.

#### Агент 4. LLM/RAG Agent

Задача:
- внедряет retrieval;
- проектирует промпты;
- выбирает места, где LLM полезен;
- убирает места, где LLM создает шум.

Артефакты:
- retrieval pipeline;
- prompt pack;
- evaluation set;
- fallback logic.

#### Агент 5. Backend Agent

Задача:
- API/бот-логика;
- новые таблицы;
- миграции;
- интеграция planner + KB + Telegram flow.

Артефакты:
- сервисы;
- контроллеры;
- migrations;
- observability hooks.

#### Агент 6. UX/Conversation Agent

Задача:
- перепроектирует диалоги;
- делает короткий и удобный onboarding;
- добавляет сбор вкусов, ограничений и обратной связи;
- улучшает объяснимость рекомендаций.

Артефакты:
- conversation map;
- новые шаги onboarding;
- тексты кнопок;
- feedback loops.

#### Агент 7. QA/Evaluation Agent

Задача:
- тестирует реалистичность меню;
- считает однообразие;
- проверяет корректность КБЖУ;
- валидирует shopping list и рецепты.

Артефакты:
- тест-кейсы;
- golden datasets;
- regression suite;
- evaluation dashboard.

### Рекомендуемая последовательность работ

1. Product/Research Agent
2. Recipe Knowledge Base Agent
3. Nutrition Planning Agent
4. Backend Agent
5. LLM/RAG Agent
6. UX/Conversation Agent

## 4. Дальнейшее развитие продукта

### Ближайшее развитие

1. Перекусы и 4-5 приемов пищи.
2. Быстрые замены блюда внутри дня.
3. Автоматическая замена ингредиентов.
4. Генерация meal prep на 2-3 дня вперед.
5. Меню по бюджету.
6. Сезонные меню.
7. Семейные меню.
8. Вегетарианские, high-protein, Mediterranean, low-carb сценарии.

### Среднесрочное развитие

1. Умный список покупок с объединением по неделям.
2. Интеграция с доставкой продуктов.
3. Фото-лог питания и сверка с меню.
4. Отслеживание соблюдения плана.
5. Еженедельная адаптация меню по фактическому поведению пользователя.
6. Персональные рекомендации "попробуй что-то новое, похожее на то, что тебе понравилось".

### Долгосрочное развитие

1. Nutrition coach: бот не только выдает меню, но и ведет пользователя по цели.
2. Профиль вкуса пользователя.
3. Социальные механики: подборки, челленджи, сохраненные любимые блюда.
4. B2B-направление:
   - white-label;
   - корпоративное wellbeing-решение;
   - бот для фитнес-экспертов и нутрициологов.

## 5. Что я бы рекомендовал делать первым

Если идти по impact/effort, я бы начал так:

1. Ослабить текущие ограничения генерации и снять 7-дневную жесткую блокировку.
2. Добавить новые поля профиля пользователя.
3. Спроектировать recipe knowledge base.
4. Загрузить стартовый качественный каталог рецептов.
5. Перевести генерацию меню с "LLM invents menu" на "system selects from recipe catalog".

Главный вывод:
- проблема не в том, что бот "плохо пишет рецепты";
- проблема в том, что у продукта пока нет рецептурного ядра и слоя персонализации вкуса;
- пока меню рождается только из промпта, оно почти неизбежно будет однообразным.
